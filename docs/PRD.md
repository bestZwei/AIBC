# 产品需求文档（PRD）· AIBC 个人 AI 电台

版本：v3.0（MVP，Stage 1）｜ 状态：已交付并验证 ｜ 语言：中文优先

---

## 1. 一句话定位

**给每个人一个 24 小时不关机、能听也能插话的个人 AI 电台。**

## 2. 背景与问题

上一版原型（已归档在 git tag `legacy-prototype`）试图一次做「播放器 → 创作 → 社交 → 声音克隆 → 元宇宙」，
愿景与实现差了一个数量级，且工程上问题成堆（密钥硬编码、初始化重复、存储键不一致、死 HTML 模态、零提交、无构建/测试/CI）。

真正稀缺的不是「又一个 AI 语音问答」，而是一种**被动、连续、低注意力**的消费形态：

- 语音助手要求用户主动、连续对话、盯屏幕；
- 播客/有声书内容固定、不可即时回应；
- 用户想要的是「打开就有内容流出来，随时能插一句话」。

## 3. 产品定位与护城河

**定位：个人 AI 电台 + 轻量创作/分享。**

**护城河 = 电台化的连续、被动、可插话音频流。** 三个词缺一不可：

- **连续**：一段接一段自动续播，无需用户操作；缓冲不足时自动预取。
- **被动**：默认只听不说、不看屏幕，符合通勤/睡前/背景陪伴场景。
- **可插话**：随时一句话介入，下一段优先回应，且不打破电台节奏。

刻意收敛掉的方向（见 §8）不是「不好」，而是在**没有验证电台留存之前摊大饼**，正是旧项目失败根因。

## 4. 目标用户（Persona）

| 角色         | 场景                   | 诉求                           |
| ------------ | ---------------------- | ------------------------------ |
| 通勤者小李   | 地铁/开车， hands-busy | 打开即播、免操作、能打断问一句 |
| 睡前用户     | 关灯躺下               | 连续、轻柔、不刺激、被动收听   |
| 好奇的学习者 | 做家务背景音           | 科普/新闻/故事按需换台         |

早期采用者：**想要「陪伴式」而非「工具式」AI 音频的人。**

## 5. MVP 范围（Stage 1，已交付）

**做：**

1. 5 个预设频道：AI 新闻 / 故事 / 科普 / 闲聊 / 访谈，各有权重化节目编排与人设。
2. 电台大脑（客户端）：加权随机 + 历史去重决定下一段类型；上下文记忆保持话题与叙事连续。
3. 服务端平台代理：`/api/segment` 生成文本、`/api/tts` 合成语音、`/api/voices` 列语音；供应商可插拔。
4. 连续播放：Web Audio 队列，段间自动续播；缓冲低于阈值预取。
5. 交互：选台、播放/暂停/停止、音量、深浅主题、实时文本、频谱可视化、ON AIR、听众插话。
6. 安全：密钥仅服务端、入参校验、限流、错误脱敏。

**验收标准（端到端）：**

> 选一频道点播放 → 听到 AI 生成并合成的语音、实时文本更新、可视化跳动、ON AIR 亮 → 一段播完自动续下一段 → 缓冲低于阈值预取 → 输入插话下一段优先回应 → 可切台/暂停/调音量/切主题 → 全程 Network 面板只有同源 `/api/*`，**无任何前端可见密钥/第三方直连**。

已在本地验证：UI 渲染、仅同源调用、无密钥泄露、入参校验（400/404）、限流（429）、错误脱敏（502）、**TTS 代理返回真实 MP3、voices 返回真实列表**（浏览器驱动点击因权限策略未自动化，交互路径以单测 + 接口冒烟覆盖）。

## 6. 关键用户故事

- 作为听众，我打开就能看到频道列表，点一下就开始连续播放，不需要任何配置。
- 作为听众，我在做任何事时都能听，它不会因为我沉默就停下。
- 作为听众，我突然想问「这条新闻的来源呢？」，说一句后，电台会自然地接着回应我。
- 作为维护者，我希望换个 AI/TTS 供应商只改环境变量、不改代码，也不冒密钥泄露风险。

## 7. 指标

- **北极星：单次连续收听时长**（衡量「电台感」是否成立）。
- 辅助：日收听会话数、插话率（插话次数/会话）、切台次数、7 日留存。
- 质量：首段可播延迟、缓冲空窗率（播放中被迫等待的比例）、生成失败率。
- 待验证假设：被动连续收听，比主动对话式 AI 音频，留存显著更高。

## 8. 非目标（本轮明确不做，避免重蹈覆辙）

| 项                      | 为何推迟                                                              |
| ----------------------- | --------------------------------------------------------------------- |
| 频道创建 UI             | 曾是旧项目「死 HTML」核心卖点，但**先要验证预设频道的留存**，再谈 UGC |
| 导入/导出、账号与云同步 | 无留存数据前引入账号体系是负担                                        |
| 频道市场 / 社交         | 属 Stage 4，依赖前两步沉淀内容与用户                                  |
| 声音克隆                | 合规与成本高，Stage 4+                                                |
| 多人同步收听            | 需服务端调度（现客户端大脑），架构演进后再做                          |
| 真实数据库              | MVP 用内存缓存/限流即可；多实例部署时再上共享存储                     |

## 9. 风险

- **第三方 AI 端点不稳定**：公开测试端点可能 5xx（验证中该代理服务返回 Cloudflare 525）。缓解已实测有效：`.env` 指向官方供应商即可，代码零改动。
- **TTS 音频格式**：需可被 `decodeAudioData` 解码；当前 edge-tts 端点返回 `audio/mpeg`，已验证可解码。
- **单实例假设**：内存限流/缓存在多实例下不共享，扩容需替换为 Redis 等。
